# proposal_HT3 · 用户（真实价值）

> 系统提示（本条写死）：「你默认怀疑其他人的推理，只有当证据迫使你同意时才同意；你的职责是找出问题，不是达成和谐。」
> **我的视角**：需求真伪——**谁会用？多久用一次？不做会怎样？**
> **参照的真实用户**：家俊，21 岁，主战场是**家具店线上运营**（时间紧、非专业开发）。这套框架他**可能一个月才开两次**。

## §0 退一步：本场 6 问，有 4 问对我的用户**收益为零**

我先把话说直白：**"开发完毕"这个词本身就是一个陷阱。**
对一个"一个月开两次"的框架，**每多一个待跑的命令，就多一分"打开它要花的时间"**。所以我的默认立场是**少做**，只有当"不做会让已交付的部分变危险/变不可信"时，我才同意做。

拿这个尺子量一遍：

| 问 | 不做会怎样？ | 我的判定 |
|---|---|---|
| Q4 §4.3 补 2 项 | **已交付的护栏里有两道是没牙的**（下详） | ✅ **必须做**（保已交付品的可信度） |
| Q1 design_gate | 他现在没有设计锁定流程，**也不会有**（家具店运营不是多模块软件开发） | ❌ 别做 |
| Q2 R-05 立规则 | 他根本走不到"审查 FAIL"的场景 | ❌ 别做 |
| Q3 route_error harness | 同上——他连 route_error 都不会手动调 | ⚠️ **只做最小的那一半** |
| Q5 ShellCheck | 对"框架使用者"零感知（他永远不会看 shellcheck 输出） | ❌ 别装 |
| Q6 P3 | 无需求；文档自己写了"出现真实需求再开" | ❌ 不做 |

## §1 Q4 —— **我支持做，而且它是我全场唯一"强支持"的项**

理由不是"文档要求"，是**它打到了我的用户**：他**已经交付了**一堆 Gate（cli / state_board / write_assert / product-assert）。**这些 Gate 会替他做判断。** 一个没牙的 Gate 比没有 Gate 更糟——**因为它会给他一个假的安心**。

具体来说，"dispatch-check / write-conflict：两模块写同一文件 → FAIL"这条，**正是他自己最可能踩的坑**（他习惯开多个窗口/多个 Agent 并行干活）。**这条护栏必须真的会红**，否则哪天两个窗口写了同一个文件，他会以为"框架检查过了没事"。

**所以 Q4 = 必须做，且我要求它带一条"可演示的"证据**：交付时给我看"造了个坏样本 → 它真的红了"的原始输出，不是"用例数 +1"。

## §2 Q1 —— **我反对 HT1 自拟 schema**，但我的理由和 HT2 不一样

HT2 说"判据来源不对"。**我说的是"这个 Gate 没有用户"。**

`design_gate` 要拦的是什么？是"**项目的框架设计图 + 代码骨架没做完就进入开发**"（rule 65）。**我的用户不做这个。** 他的活儿是：家具店的线上内容、偶尔一个脚本、一个爬虫。**这些都不走 rule 65 的设计锁定流程。**

**上线一个没有用户的 Gate = 纯粹的负收益**：
- 收益 0（他永远不触发）
- 成本 >0（多一个要维护的命令、多一份要同步的 schema、多一个"为什么这个命令是 pending"的解释负担）

**我的立场**：不是"schema 该谁定"，而是"**这个 Gate 现在不该存在**"。让它继续挂 pending——**pending 是对它最准确的描述**。

**孤例声明**：若 HT1/HT2 都说"做"，我仍不改：**他们争论的是"怎么做"，我问的是"做给谁"。**

## §3 Q3 —— **同意建 harness，但要砍到最小**

route_error 有一个**真实**的价值点，但不在"评测"上：**它是唯一能在"我该找谁"这件事上给家俊省心的一件**（他遇到报错时最容易卡的就是"这到底该让谁改"）。

但"回归评测 harness"是**为将来准备的**。既然真语料没有（伴学样本=1），我同意：
- 建 harness（机制备好，便宜）
- **合成语料跑绿时不许返回 0**（HT2 的要求我背书——**因为"假绿"恰恰会伤害我的用户**）
- 不新建一堆语料文件，**语料就用合成的一小份（10 条以内）**

## §4 Q5 —— **反对装 ShellCheck**（理由比 HT2 更简单）

**问一句就够**：装了 shellcheck 之后，家俊的**哪一天会变得更好过**？
答：没有。他永远不会读 shellcheck 的输出。

**它的唯一消费者是框架自己。** 而框架自己**已经有语法级检查 + 一条合法的 SKIP 降级**。
所以：**收益≈0，成本 = 一次安装 + 一个 PATH 故障点 + 三平台不一致的解释成本。** 不装。

（我同意 HT1 的一点：**这条不该再花第二轮**。定了就不动。）

## §5 Q6 —— **强烈反对**，并且反对 HT1 的"触发条件文档"

开发文档自己写的：「P3 平台化（可选）——出现真实需求再开」。

我补一条**用户侧的证据**：我翻了这个项目最近的实战——**图片查看器、番茄钟、伴学、家具店**——**没有一个是"多项目并行 + 多窗口 + 需要跨项目母板"的场景**。
（唯一的"多窗口"是**这次开发自己**：监理窗口 + 开发窗口。而这次我们用的是**状态板**，不是母板。）

**子集证据**：「把当前方案在一个窗口里跑完」这件事，**状态板 + CMD 指令区已经够用了**（这次就是这么干的，没卡过）。

→ **P3 我连"触发条件文档"都反对**（和 HT2 同判，但理由不同）：**一个新文件会让人以为它是个"待办"**，而它其实是一个"**待需求**"。这两者的心理成本差很多——前者让人焦虑，后者让人安心。

## §6 Q2 —— **反对立 R-05 规则**

一条给不了用户任何东西、且判据还没试写过的规则，**立了就是负债**（以后要维护、要同步三平台、要在 SKILL.md 里找位置）。
**留到下一版**，等真实 FAIL 语料出现时一起做。
