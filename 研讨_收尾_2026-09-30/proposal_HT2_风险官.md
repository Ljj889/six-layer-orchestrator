## §0 退一步：本场真正危险的动作是"把 pending 换成绿"

本场 6 问里，**有 4 问的诱惑都是同一个**：
> "既然还能做，那就做完它，进度就 100% 了。"

**这是最危险的方向。** 因为本项目的 pending 不是"没来得及做"，而是**三条被显式设计出来的诚实边界**：
- `design_gate` pending = **schema 未定稿**（文档硬门）
- `route_error` 回归评测 pending = **样本数 = 1**（rule 5）
- ShellCheck SKIP = **本机无该能力**（D-09 三态）

它们全部来自**收敛过的决策**，不是遗漏。**把 pending 变成绿的唯一合法路径，是让当初拦住它的那个条件真的消失**；否则就是把"未验证"洗成"已验证"——而这恰好是 v3.19.0 已经实证过一次的错误（`re.S` 让检查器说谎）。

## §1 Q1 —— **我反对自拟 schema 并立即实现 `design_gate`**

HT1 拿 `engine_config` 类比，说"参数也是我们自拟的，标注来源就没事"。**这个类比有一处致命的不对称**：

| | `engine_config` | `design_gate` schema |
|---|---|---|
| 内容是什么 | **技术参数**（档位域、超时、预算） | **人的确认行为**（谁确认了、确认了什么） |
| 谁来定 | 开发方（技术判断） | **人**（rule 65：设计锁定 = 人机共同确认） |
| 错了会怎样 | 越域即 FAIL，**当场暴露** | **静默** —— schema 写错，`design_gate` 会一本正经地判"设计已锁定"，而真实的设计确认可能根本没发生 |
| 有外部判据吗 | 有（L0 实测可裁决） | **没有**（我自拟的"确认清单"无法被任何实测证伪） |

**关键分歧**：`engine_config` 自拟是安全的，因为它**有外部判据**（L0 一跑就知道对不对）；`design_gate` schema **没有**——它是**关于人的流程的规格**，只有家俊能定义"什么样的确认才算数"。**我们自拟 = 定义了一个不可证伪的判据，然后拿它给自己发绿。**

而且 `design_gate` 的危险等级更高：它的产物不是"报告"，是**一道 Gate**。Gate 判错 = 后续流程被错误放行。

**我的立场：维持 pending，但把"解除条件"写清楚**（缺哪几项、家俊给到什么粒度就能定稿）。**这是把 pending 变成"可解除的 pending"，而不是把 pending 变成绿。**

**孤例声明**：若 HT1/HT3 都投"自拟"，我仍不改。理由见上表——这不是口味分歧，是**判据来源**分歧。

## §2 Q3 —— **我反对把"建 harness"记作"回归评测已推进"，除非标签是硬拦**

HT1 的方案是"打印 `corpus_kind=synthetic`"。**我的问题是：谁读那行？**

本项目刚刚实证过一件事：**状态板的弱校验报"单调不减 ✓"，而 append 其实写错了地方、行数根本没动。** 检查器没错，**它只是管不到那一层**。
同一族风险：`route_error --eval` 打印 `corpus_kind=synthetic` → 人类/Agent 扫一眼看到"全绿" → **标签没人读**。

**要求（否则我投反对）**：
1. 合成语料跑绿时，退出码**不得为 0**（用 `3 = PENDING` 或 `1`），否则 CI/Gate 会把它当通过；
2. `--status` 的 PENDING 列表**由代码里的常量决定，不由输出文本决定**；
3. harness 的 `corpus_kind` 必须**同时**出现在**报告头**和**退出码语义**里 —— **两个信号不一致就是 FAIL**。

**满足这三条，我同意建 harness**（它确实是净收益：机制先备好，真语料一到就能跑）。

## §3 Q5 —— **我反对装 ShellCheck**（三条理由，按强度排序）

1. **工具可用 ≠ 流程会跑它。**【强】用例 7 里"有 shellcheck 就走语义级"这条分支，**本轮之前根本不存在**——是刚刚才加的。也就是说：**过去很长一段时间里，即使装了 shellcheck，也没人会调用它。** 加装工具不产生"被调用"这件事；**分支已经写好了，这就够了**。
2. **本机 PATH 已经坑过我们三次。**【强·实测】本轮实证：裸 `bash` → WSL 别名（被沙箱黑名单拦）；`py.exe` 启动器 broken；node 只在受管目录。**多装一个需要 PATH 解析的外部二进制 = 多一个同族故障点。** 而 shellcheck 的价值是"语义级 lint"，**它不是任何 Gate 的硬依赖**。
3. **三平台副本不共享工具。**【中】`sync_to_platforms` 分发的是 `.py/.md`，**工具不在分发面内**。所以 CodeBuddy / Codex 侧仍然是 SKIP。→ **本机装了 = 只有本机从 SKIP 变 PASS**，制造"三平台行为不一致"这个新的解释成本。

**我的立场**：维持 `SKIP + [不可测·工具缺失]`。**这是文档给的合法降级路径**（D-09 / D-16 用例 7 都明文允许）。**装它是"感觉更完整"，不是"更正确"。**

## §4 Q6 —— P3：**同意不开**，但**反对**为它产出"触发条件"文档

HT1 要产出 `P3_触发条件.md`。**我反对，理由是它会让文件腐烂。**

写一份"将来什么条件下做 P3"的文档，本质是**给一个尚未被需求证明的东西建档**。本项目刚立过一条规则：**僵尸能力红线（rule 72）——没有调用点的能力 = 僵尸**。一份没有触发者、没人会读的"触发条件"文档，是同一族的东西。

**更省的替代**：把这 4 条 P3 项**写进开发文档 §1.3 分期地图下方一行**（那里本来就是它的位置），**不新建文件**。

## §5 Q1 追加 —— 我要给 `design_gate` 加一条**回滚纪律**

无论本场怎么裁，有一条必须落：**`design_gate` 一旦实现，默认状态必须是"未启用"**（和状态板模板一样，D-02 的先例）。
理由：`design_gate` 是**Gate**。一个默认启用的、判据来源不明的 Gate，会在未知项目上**无差别拦人**。默认未启用 = 出问题最多是"该拦的没拦"，不会变成"不该拦的乱拦"。
