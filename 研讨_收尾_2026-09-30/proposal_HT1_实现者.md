## §2 Q1 —— `design_gate`：我认为**可以自拟 schema 并实现**，但要加一道"来源标注"闸

反对意见（我预判 HT2）：自拟 schema 会让 `design_gate` 从"诚实 pending"变成"一个对错不明的绿"。

**我的实测反驳依据**：本项目的 `engine_config` 就是这么做的——
```
$ python scripts/cli.py params
[engine_config] llm.reasoning_effort=high source=engine_config.json
[engine_config] llm.model_whitelist=['deepseek-flash','deepseek-v4-pro'] source=engine_config.json
```
`engine_config` 的**内容**（白名单、档位域）**全部是开发方自拟的**，但我们给每一键标了 **schema + 合法域 + 来源**，并且 L0 实测后**就地收紧了合法域**（`none` 被踢出去）。它现在是可信的——不是因为"我们拟得对"，而是因为**每次执行都会校验、越域即 FAIL、且来源可追**。

→ 同样的做法可以搬给 `design_gate`：**schema 标 `v1.0-draft（未经家俊确认）`**，`design_gate` 每次执行**打印 schema 版本与草案标记**，一旦家俊给正式版就升号。**"草案"三个字本身就是防假绿的闸**——它不会让任何人误读成"设计锁定已完备"。

**建议**：schema 定稿为**最小可判定集**（每项 id / 谁确认 / 确认时间 / 未确认项处置），实现 `check` 与 `--finalize` 两条路径。

## §3 Q3 —— `route_error` 回归评测：**建 harness，但让标签顶住假绿**

合成语料自测通过 ≠ 真语料可用，这个批评我接受一半。**区别在标签**：
- 我建议 harness 输出**强制打印** `corpus_kind=synthetic` 或 `corpus_kind=real`；
- 合成语料的用例数**不计入"回归评测已通过"**，只计入"harness 可用"；
- `--status` 的 PENDING 列表**只有 `corpus_kind=real` 且全绿时才移除**。

这样"建 harness"是**真交付**（机制齐了），而"回归评测"**仍诚实挂 pending**。**两件事分开报**，不混。

## §4 Q5 —— ShellCheck：**我实测了，能装，但我改变主张**

```
$ command -v shellcheck   → (空)
$ command -v scoop        → /d/scoop/shims/scoop
```
能装。但我跑完这条命令后意识到 HT2 会问的那个问题更硬：**装了它，谁会调它？**
`six_layer_check` 的用例 7 已经是"有 shellcheck 就走语义级，没有就语法级 PASS + 另立 SKIP"。**也就是说代码路径早就写好了，缺的只是工具本身。**

→ **主张：装**（`scoop install shellcheck`，dev-only，不违反 K-6 的"运行时 0 依赖"）。理由：**这是一行命令换掉一条永久 SKIP**，成本/收益比值太高了。**但如果装失败（网络/沙箱），不许为此再花第二轮** —— 维持 SKIP + 未验证即可，那本来就是文档给的合法降级路径。
