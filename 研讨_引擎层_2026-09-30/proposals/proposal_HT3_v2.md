## §A 信息引导（K11，先答后审）

### A1. 我从"用户视角"看到、别人可能还没考虑到的关键信息（≥1 条）

**信息一：四家的记账单位全错了——都在算"AI 工时/轮数"，没人算"家俊分钟"。**

**信息二：本轮研讨过程本身就是"系统太重"的实证，而且是可计量的。**

**信息四：我手里没有"使用频率"这个决定性数据，我不会假装有。**
我能从证据推出的只有"成本侧"；**收益侧的分子（这套框架救过几次、在哪几个项目救的）我一无所知**。所以我把 P2 的绝大多数条目挂在一个**必须由家俊回答的决策点**上（见文末清单），而不是替他拍板"要做/不要做"。**这是我与 HT1/HT2 最大的方法论差异：他们已默认"要做"，我认为"做不做"本身是未决问题。**

## §B 交叉互审质疑（K3 六要素）

### 质疑一 · 点名 HT1「D-02 把 (c) 提前到 P2 + 与 D-22(b) 合并」：把"强制力"押在一个结构上做不到的校验上

- **问题**：HT1 主张 P1 采纳 D-02(a) 模板、**P2 提前做 `cli.py status append|check`**，用"校验事件流是否新增"给"只在对话里说不算"提供强制力。
- **影响**：这正是 HT4 §6 预言的失败形态——**"板子建了、事件流一行不加，但文件存在 → 看起来'有状态板'"**。因为 [HT2 质疑2] 已实测：**脚本无法知道"用户做没做某动作"，只能判断"文件改没改"**；而 [HT4 A11] 指出多窗口并发写下"事件流是否新增"的校验**天然误报**（基线存哪、如何加锁都没定）。于是这条"强制力"会产出**一个既拦不住、又会误报的 Gate**——即 [S4] 点名的那类**"形式通过而非实质通过"**。HT1 用"判据1 不通过（没有落盘入口就是口号）"来正当化提前做 (c)，但**判据1 的解法不是"随便加个脚本"，而是"加一个真能判定的脚本"**；判定不了，加脚本只是把口号变成假绿。
- **等级**：**P1**（会造出新假绿，且伪装有强制力）
- **证据**：[HT2 质疑2 / 实测附录 C]；[HT4 A11 隐含假设表]；[HT4 §6 D-02 行]；[S4]"用例 7 只跑 `bash -n`"= 现成的"形式通过"样本。
- **建议**：D-02 在 P2 **不做 (c)**。最小可用形态 = **AI 在对话窗口写事件流 + 家俊只说一句"记一下"**（家俊边际成本≈0，且不存在"脚本判定用户动作"这个做不到的校验）；"事件流是否新增"的校验留到 P3、且必须先解并发基线（HT4 前置）。
- **证据增益**：把"强制力"从**一个会误报的脚本**改回**一个 AI 的习惯**——前者造假绿，后者最坏只是"AI 没写"，而后者可以用"事件流行数 vs AI 行动数"人工抽查一次即可发现，不引入新的信任风险。

### 质疑二 · 点名 HT1 + HT2 的 F1 之争**共同缺失一个变量**：轮数不是收益

- **问题**：HT1 主张"一条依赖链一次做完（否则 enforcement 无机读账本、compress 无调用层、温度无宿主 = 空壳）"，HT2 主张"拆 P2a/P2b、真实 4-6 轮"。**双方都在争"怎么切/几轮"，但没有任何一方给出"这套引擎每周被用几次"的数据**——而这是决定"值不值得切、值不值得做"的唯一分母。
- **影响**：如果不问使用频率就开工，结果是**花 4-6 轮建一个低频引擎**：HT1 的"空壳"担心和 HT2 的"工期"担心都成立，但**它们都只在"确实高频要用"的前提下才值得解决**。若家俊的主战场（家具店运营）根本不走六层框架，则 HT1 的"一次做完"= 一次性把资源投进一个低频工具，HT2 的"4-6 轮"= 把投资翻倍——**两人谁对都无关紧要，因为可能根本不该做。**
- **等级**：**P1**（决定 P2 是否立项，而非怎么立项）
- **证据**：框架现状（83 条规则 / banner 实测 8129 字符 / 7 脚本）；[task-brief §1] 家俊最高优先级项目 = **家具店线上运营**（运营类，非多模块软件开发）；讨论文档 §一"已知缺口"里 LLM 调用层缺口来自 rule 56 的"**迁移时**替换为 Python 硬代码"——**迁移从未发生**；全套材料**无一条使用频率数据**。
- **建议**：开发文档**第一行**加一道前置门：**家俊回答"过去 30 天框架真实使用次数 + 用在哪些项目"**。低于阈值 → P2 只做 `cli.py` 串联 + 自测网（这两件对任何频率都正向），LLM 层/route_error/enforcement/compress/design **全部挂起**。
- **证据增益**：把"要不要建引擎"从**偏好之争**变成**数据之争**；也给 HT1/HT2 一个共同的、可判定的收敛出口——省掉一轮"建完才发现没人用"的浪费。

### 质疑三 · 点名 HT2「D-13 的 P2 落 (b) 告警 + (c) 超限问人」

- **问题**：HT2 自己实测"**子 Agent 走 WorkBuddy 原生 Agent 工具，不经过 cli.py**"，却仍把 **(c) 超限问人**列进 P2。若真实调用根本不经过引擎，那么 **(c) 的中断也拦不住真实调用**——它只会在**引擎自己调 LLM**的那点流量（若有）上触发，而那部分流量恰恰是最不重要的。
- **影响**：家俊会**被一个拦不住主流量、只能拦边缘流量**的中断打扰；而 [HT2 实测] 已证明本机只有 1 个模型、成本控制价值有限。这是我 R1"确认疲劳"论点的**加强版证据**：不只是"怕麻烦"，而是**这个麻烦买不到对应的保护**。
- **等级**：**P1**
- **证据**：[HT2 §1 D-13 / 质疑1 实测]（子 Agent 绕过 cli.py）；[HT2 D-13 建议"P2 只做 (b)+(c)"与上述实测**自相矛盾**]。
- **建议**：P2 只做 **(b) 告警**；(c) **延后到"第一次真实超支事件发生之后"**再加。若 HT2 能举证"存在必经引擎的高频调用路径"，我撤回本条。
- **证据增益**：省掉一个买不到保护的中断；也避免给家俊建立"引擎在管成本"的错误安全感（HT4 反复警告的"假绿"同族）。

> 补充（P2 级、不计入上面三条）：**点名 HT1 D-04 载体换位 vs HT2 D-04 采纳(b)**。我 R1 选 (b)，但 HT1 的理由（**rule 79 是可 grep 的 Gate，"接缝 vs 通道"是测试设计判断，塞进去会让 rule 79 变语义垃圾场**）在证据上更硬。我**接受 HT1 的 (c) 为主 + (b) 只留一句引用**，见 §C。
