## §0 退一步

这份方案真正要解决的，不是"再加 22 条规则"，而是**把"框架靠 Agent 自觉记得"这件事，一批一批换成"跑一下就知道对不对"**——即用 rule 64 的引擎化判据，给 LLM 装外骨骼。

它最可能在三个地方失败：① **层级没分清**——22 条里混着"框架仓库自举"（D-08/D-09/D-18/D-21）、"引擎本体"（D-10…D-16）、"用户项目产物"（D-02/D-03/D-19/D-22）三类东西，却共用一套"三期"和一套"出口"，于是 P1 的验收口（三平台一致）和它声称要交付的产物（状态板标配）根本不是一个层的东西；② **引擎化的强制力悬空**——D-02 要"只在对话里说不算"，可它的唯一强制手段（D-22 极简入口）被推到 P3，中间两期是口号；③ **依赖顺序被"分期"掩盖**——`compress` 依赖 LLM 调用层、enforcement 依赖尚不存在的机读账本、分阶段温度依赖调用层宿主，P2 被当成"一个盒子"，实际里面是一条有向图，不排图就会做出空壳。

我的立场：**方向我认，22 条我一条不驳**；但**拼装方式和分期我要求重排**——否则这套方案会"每条都对、合起来漏"。

## §2 我的三条最强质疑（K3 六要素）

### 质疑 1 · P2 被当成"一个盒子"，实际是一张有向图；D-13 与 D-14 会做成空壳

- **问题**：D-13「调用前 enforcement」需要一个**机读的累计用量数据源**，但现状 `cost_log.md` 是**事后 append-only 定长行**（rule 38/53，`cost_log.py` 只有 `add/summary/audit/tail`，没有"读累计供拦截"的接口）；D-14 需要一个**回归语料**，但伴学 FAIL 语料尚是单项目、且"误报样本"混在其中。三条建议（D-11/D-13/D-14）被并列写进 P2，没有先后。
- **影响**：enforcement 要么做不出来、要么退化成本身被 rule 57 明文禁止的"事后告警"；route_error 的评测要么无法跑、要么把"误报真伪"和"路由类别"两个正交问题混在一起测，结论不可用。**P2 交付一个"看起来有、实际空转"的壳**——这是本项目最典型、也最难验收的失败模式。
- **等级**：**P0**
- **证据**：`SKILL.md` rule 57 原文"**监控告警 ≠ 调用前拦截**，成本控制必须在调用发生之前执行"；`scripts/cost_log.py` docstring（定长行 append，无累计读接口）；`references/error_routing.md` v1.0 自述"当前 WorkBuddy 版由调度器 prompt 判断"——即**规则表是从零起，不是从半成品起**；`蒸馏候选_伴学P0` §D 自述"样本数=1"。
- **建议**：在开发文档里给 P2 画**显式依赖图**并把三件事串成一条链：`token_ledger（新建）→ D-11 调用层 → D-12③ 温度 / D-13 enforcement / compress`，`D-14` 独立但**必须先用合成样本跑通语法级单测**再把伴学样本当 `[假设]` 回归集；enforcement 判定函数必须由 D-16 自测覆盖（预算内放行 / 超限拦截 / 超限问人）。
- **证据增益**：把 P2 从"2-3 轮的黑盒"变成"可逐个断言的链条"；每条链上组件都有可核对的输入输出，避免"整套跑通但没有任何一条被真正验证"。

### 质疑 2 · 22 条混了三个层级（元层 / 引擎层 / 产物层），却被一套"三期 + 一套出口"压着；P1"1 轮"不成立

- **问题**：D-08/D-09/D-18/D-21 管的是**框架仓库自举**；D-10…D-16 管的是**引擎本体**；D-02/D-03/D-19/D-22 管的是**用户项目产物**。三类东西共用"P1/P2/P3"，于是 P1 的验收出口写成"三平台版本一致 + six_layer_check 自检通过 + 索引可 grep"——这是**元层出口**，却挂在还包含"状态板标配"（产物层）的同一期上；而"P1 一轮落地 9 条"忽略了：rule 58 的 Phase 7 Gate 要求**用户逐条确认**（一次人命），D-08 改 `SKILL.md` 后必然触发 D-09 的**第二次** sync。
- **影响**：① P1 的"可停"是假的——停在半路会留下"三平台不一致"的中间态；② 后续期把两类动作（改规则 / 分发）混在三平台同步里，每次 sync 都要背负未完成项；③ 用同一套"出口"验收不同层的交付，会出现"元层绿了、产物层没动"却整体标绿。
- **等级**：**P1**
- **证据**：讨论文档 §六 P1 出口行；`SKILL.md` rule 58 六步流程（含 Gate：用户逐条确认采纳）；rule 76 落盘四步（含 Sync）；D-08 的 banner 与 D-09 的 sync 互为上下游。
- **建议**：① 开发文档里**先把 22 条按三层重排**（元层 / 引擎层 / 产物层），每层各自给"分期 + 出口 + 回滚"；② P1 拆 **P1a（规则修订+Gate 确认）/ P1b（升版+banner 治理+sync+校验）**，明确 **D-08 先于 D-09**；③ P1 的出口对**产物层**条目（D-02/D-03）单独写一句"本期只交模板+规则，状态板脚本化在 P2 —— 出口 = 模板可复制、`_index.md` 可检索到"。
- **证据增益**：每一期有独立、可停、可回滚的边界；把"三平台一致"从"混在所有事里的一道口"变成"元层专属的一道门"，避免用它给产物层背书。

### 质疑 3 · D-18 与 D-12③/D-13 的"真相源边界"没划，落地即产生第二真相源

- **等级**：**P1**
- **证据**：`SKILL.md` rule 56 接口定义含 `"temperature": 0.0`；rule 72（僵尸能力 / 第二真相源 / 备份双实现互为第二真相源）；讨论文档 D-18 原文与 D-12③/D-13 原文并列。

## §3 开源复用视角（我的角色下：最该复用 / 最该自建）

> 本轮我禁网，**只给方向与项目名，不给 URL / License / 版本**——那些由扫描员核实。原则：**零依赖是硬约束（task-brief §2.1），所以"复用"绝大多数指"复用设计/用例"，不是"引入依赖"。**

1. **`cli.py` 命令编排 → 借鉴 `pre-commit` 的"配置驱动 + 多 check 聚合 + hook 生命周期"架构（自建，不引依赖）**。它的价值不在代码，在**"一堆独立 check 由一个入口按声明顺序跑、各自可跳过、失败可定位"**这个模型——正好对应 D-15"串联 7 脚本"。用 stdlib `argparse` 复刻其骨架即可；**引入 `pre-commit` 本体 = 违反零依赖，明确不引**。
2. **零依赖 SSE/HTTP → 借 `openai-python` / `httpx-sse` 的"边界用例清单"，不借代码**。手写 SSE 的坑是**心跳帧、多行 `data:`、`[DONE]` 终止、`usage` 只在尾帧、中途断流**——这些用例清单（不是实现）可直接喂给 D-16 的自测网。**只抄用例、不抄实现**，规避 License 污染（是否可读代码由扫描员定）。
3. **状态板 / 事件流 → 借 `adr-tools` 与 `Keep a Changelog` 的"单一 markdown + append-only + 可 grep 编号"做法（自建）**。`PROJECT_STATUS.md` 的三分区（状态/CMD 指令区/事件流）与之同构：编号只增（CMD-NN / 事件行）、原文不改、状态就地标。**这个模式比任何库都适合"零依赖 + 人可读 + 可 grep"三重约束。**
4. **状态机 / 压缩 / 编排引擎 → 明确"不引入"清单**：`transitions`(pytransitions) 的设计思想（转移表 + 非法转移拒绝）`lifecycle.py` 已同构，**只借设计不引库**；`LLMLingua`（上下文压缩）需依赖 + 模型、`LangGraph`/`CrewAI`/`Prefect` 需重架构 + 依赖——**在"零依赖、单人自用、只做闸不做平台"的目标下，统统不适合本轮**。它们值得的是"架构参照"，不是"选型候选"。

**一句话**：本轮该复用的是**别人的失败用例与结构模式**，不是别人的依赖；凡是会让 `python + stdlib` 这个前提失效的，一律自建。

## §4 我认为原文档漏掉的议题（3 条）

1. **「项目根」的单一定义 + 框架自举**（D-02 × D-15 × D-19 的交叉盲区）。原文档三处都默认"项目根"显然存在，但没定义。必须补：**项目根 = cli.py 首个位置参数 = 数据三件（`progress.json`/`PROJECT_STATUS.md`/`cost_log.md`）所在目录**；并明确**框架仓库自身也是项目根**——否则"状态板升格为标配"只覆盖用户项目，框架自己改自己时反而没有状态板（dogfooding 断裂）。
2. **用户项目运行时用"哪个平台副本"的引擎**（D-09 × D-15 × D-19 的交叉盲区）。三平台各有一份 `cli.py`（rule 76：平台目录是只读副本）。用户项目跑 Gate 时，用的是"当前平台那份"还是"仓库那份"？两份版本漂移时谁说了算？原文档只讲了"如何分发"，没讲"运行时如何寻址 + 版本如何核对"。必须补一条寻址与版本一致性约定（可复用 runtime_probe 的 `[PROBE]` 口径）。
3. **"审查 FAIL 真伪甄别"议题**（从 D-14 剥离）。D-14 把"审查误报"混进 `route_error` 回归集，但**误报是"FAIL 判定本身可信吗"，路由是"错误类型→哪个角色"**，两者正交。原文档在 D-14 里点出了"含审查误报样本"却没收成议题——这是个独立缺口（v3.19.0 的 `render-silent-fail` 误报教训已证明"检查器自己会说谎"）。建议单列：**审查结论必须带"可信度标签 + 独立取证"**（呼应 rule 79 v3.15.0 的"改动范围对焦 + 独立取证"）。
