# HT-用户 · Round 1 独立盲写提案

> 视角：需求真伪。默认立场：专挑"没人要 / 过度设计 / 自嗨"。
> 立场纪律：只有当证据迫使时我才同意；我的职责是找出问题，不是达成和谐。
> 锚点：本框架的**唯一真实用户是家俊一个人**（21 岁，非专业开发者，"用 AI 放大一个人干活效率"）。判断一切议题的第一问是——**"落地后，家俊每周要额外付出多少分钟？换来的确定性值这个价吗？"**

---

## §0 退一步（3-5 句）

这个方案真正要解决的问题，按原文是"把只能靠自觉的规则下沉为引擎"。但**家俊嘴上要的和方案在做的是两件事**：他要的是"少出错、少返工、AI 别自己跑歪、别让我当人肉消息总线"——这些**90% 在规则层（P1）就能治**；而方案的重心（P2 的 LLM 调用层 / route_error / enforcement / cli.py）解决的是**"框架自己的工程优雅"**，跟家俊的每周时间几乎无关。

它会失败的第一种情况：**家俊的主战场（家具店运营，最高优先级）根本不走六层框架**——那给一个低频工具造引擎，就是在给一辆一个月开两次的车换赛车引擎。

它会失败的第二种情况：**"要多写文档/多确认"的条目（D-02 状态板 / D-03 交接件 / D-21 讨论文档 / D-13 拦截问人 / D-16 硬 Gate）单独看每条都便宜，叠起来 = 确认疲劳**——家俊最终会**绕过框架**去干正事，平台建好了没人用。

它会失败的第三种情况：原文档说的"上限：规则层 + 引擎层"，但真实证据（SKILL.md 已 v3.20.0、83 条规则、7 个脚本、banner 数千字、22 议题讨论稿）表明——**这套系统本身已经成为家俊的负担源**。再加一层引擎，不是减负，可能是压垮。

## §2 我的三条最强质疑（K3 六要素）

### 质疑一：P2「引擎层本体」整体是"为框架而框架"——家俊不需要引擎，他需要少返工

- **问题**：把 P2 的重心（LLM 调用层 + route_error + 调用前 enforcement + 三个新命令）当成"地基"来建，但这四样**全部是"框架自己运行得更优雅"**，不是"家俊的项目更少错"。
- **影响**：这是**数百到上千分钟的 AI 工作**（AI 辅助下约数天到一周），换来的多是"框架内部的整洁"；家俊的家具店运营、Vlog 剪辑**一点没变快**。
- **等级**：**P0（可能做错方向）**。
- **证据**：① 现状快照：框架已 v3.20.0、83 条规则、7 个脚本、banner 数千字——**系统本身已是负担源**；② 家俊最高优先级项目是"家具店运营"，这类运营/剪辑工作**几乎用不到六层框架的引擎**（它本来就是给"多模块软件并行开发"用的）；③ 原文自己也把 UI/平台化判为"不产生价值"——**同一逻辑该往上追一层：P2 里"没有真实调用方"的部分，同样不产生价值**。
- **建议**：P2 砍到"**cli 串联现有 7 脚本 + 自测网**"两件；LLM 层 / route_error / enforcement **全部先答"有没有真实调用方"**，答不出就不做（D-11/13/14 待定）。
- **证据增益**：**一个前置问题就能砍掉 P2 一半工作量**——"过去 30 天，哪个真实任务因为缺 LLM 调用层 / route_error 而卡住或返工？"若答不出，就是需求不存在。

### 质疑二：6 条蒸馏候选全部来自"单个项目一轮实战"，却要升为新 rule 84 + 框架级标配——样本数=1 的过度泛化

- **问题**：D-01 要新开 rule 84，D-02 要升格"框架级标配"，D-03 要"换窗必做"——**全部只被伴学 P0 一个项目、一轮实战验证过**。原文 §九判据 3 和候选件 §D 自己都写了"样本数=1、应标 `[假设]`"。
- **影响**：从**一个项目**的摩擦推出**全局规则**，会在不匹配的项目上产生**假阳性负担**（例：家具店运营项目被迫建状态板、写交接件，全无用）。
- **等级**：**P0**。
- **证据**：蒸馏候选 §D 明写"以上全部来自单个项目（伴学 P0）的一次实战 → 样本数 = 1 ✗，跨项目可复用性未经检验"；原文 §九判据 3 自己规定"第二个项目复现才升 `[事实]`"。
- **建议**：D-01/D-02/D-03 一律**先标 `[假设]`、只在一个项目试运行**（rule 47 B1 思路），**第二个项目复现才升格**为框架级/新 rule。**不许一次实战就动编号体系。**
- **证据增益**：把"新规则"降为"候选假设试运行"，**预防 5-10 条永不触发的死规则**（现有 83 条里已有 6 个删除号，说明这坑踩过）。

### 质疑三：四条"要人多做一步"的条目叠加=确认疲劳，家俊会绕过框架

- **问题**：D-02（"只在对话里说不算"）、D-13（超限问人）、D-16（硬 Gate 视为未完成）、D-21（固化为 Phase -1.5 前置件）**单独看每条都合理、都便宜**；但它们是**同一批落地**、作用在**同一个人**身上。
- **影响**：家俊每次干活要：写事件流 + 被 AI 问预算 + 被 Gate 卡"未完成" + 写讨论稿回填。**累加到"不如不用框架"的临界点，框架就死了**——建得再漂亮，没人用=0 价值。
- **等级**：**P0（决定成败的是采用率，不是功能）**。
- **证据**：rule 66 v3.17.0 已专门做"确认分级（回退成本×方向性）"，说明确认疲劳**早已是已知痛点**；本次又新增 D-13/D-16/D-21，**方向在加重而非减轻**。
- **建议**：四条**合并算总账**——同一"决策日"只允许新增**至多一条**"必须问人/必须多写"的环节；其余改**异步**（AI 做完、事后可查，不打断家俊）。D-13 直接降为"只告警"（见 §1）。
- **证据增益**：**用"每周额外分钟数"这一个可算指标**做准入线（建议阈值：新增环节 ≤ 5 分钟/周），比"每条是否好看"可靠得多。

## §3 开源复用视角（我的角色下：能复用就别自建）

1. **CHANGELOG 不要自造规范（D-08）**：直接采用 **Keep a Changelog** 的格式约定（约定成熟、人/AI 都能读），省一次"自己定格式"的成本。**能不设计就不设计。**
2. **状态板/看板不要自建引擎（D-02/D-19）**：真要可视化，**Obsidian / GitHub Projects 的现成看板**比自建 `PROJECT_STATUS.md` 引擎便宜得多；家俊已有笔记库生态。**自建引擎的前提是"现成的都不够用"——先证明这一点。**
3. **"用户极简入口"(D-22 b) 用现成件**：一句"记一下"触发落盘已够；真要按钮，**双击一个 `.bat`** 就是入口，**不值得自建入口页**。
4. **LLM 调用层（D-11）真要做也别从零手搓 SSE**：这是扫描员 A 的活，但**从用户价值看**——如果"框架脚本自己调 LLM"需求不存在，**连复用的必要都没有**；存在的话，优先复用成熟件而非手写 SSE（手写=未来自己维护 SSE 格式漂移）。

## §4 我认为原文档漏掉的议题

1. **"过去 30 天，这套框架被真实用过几次？用在哪几个项目？"** —— 原文档通篇在算"AI 要多做什么"，**没有一条问"这套框架的实际使用频率与场景"**。若家具店运营/剪辑几乎不用六层框架，则引擎层是给低频工具的奢侈投资。**这是决定 P2 做不做的第一数据。**
2. **"家俊本人的时间预算"** —— 22 个议题没有一条算"家俊每周要为此多花多少分钟"。**建议每个新增环节强制标注"家俊成本（分钟/周）"**，超过阈值直接驳。
3. **"回退/停用预案"** —— 没有一个议题问"若引擎层做完不好用，怎么退回 v3.20.0？"**只增不删 + 不做回滚 = 单向膨胀**（banner 数千字就是前车之鉴）。

| **D-16 硬 Gate** | 限"**引擎脚本**"；非引擎不卡。 |
| **D-09 三平台同步** | 先盘点**实际打开过几个平台**，用不到的直接砍。 |

## 一句话总结：我认为这个方案最大的"自嗨风险"

**最大的自嗨风险是——把"框架自己运行得更优雅"当成了"家俊的活儿变得更好干"。**

整套 P2 引擎层（LLM 调用层 / route_error / enforcement / 新命令）在技术上是漂亮的、逻辑上自洽的、讨论起来很过瘾的；但它的**用户是一个时间紧、非专业、主战场（家具店运营）可能根本不走六层框架的人**。**判断标准只有一条：落地后家俊每周多花几分钟、少返工几次。** 若这条账算不过来，引擎建得越漂亮，越是"给一辆一个月开两次的车换赛车引擎"——**而 83 条规则、数千字 banner、22 议题讨论稿，已经在提醒：这套系统的主要风险不是"不够强"，而是"太重、没人用"。**
