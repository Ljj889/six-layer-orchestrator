## §A 信息引导（K11 · 先答后审）

### A-1. 我从我的视角看到、别人可能还没考虑到的关键信息

**① 自产实测：自测用例数有四种口径，全不一样——这是"元层假绿"。**
我实跑 `python scripts/six_layer_check.py self-test`，本机输出尾行：

```
总计：26 PASS / 0 FAIL / 1 SKIP
```

再对源码 `add("...")` 做正则统计：**30 处注册**（其中 `sync_to_platforms.ps1 语法解析` 有 2 处 if/else 分支、`sync_to_platforms.sh 语法检查（bash -n）` 有 **3 处**分支）→ 去重后**实际执行 27 项**（26 PASS + 1 SKIP）。

于是同一件事有四个数字：

| 来源 | 数字 |
|---|---|
| 讨论文档 D-16 | **24 条** |
| 任务书 / `[S4]` | **25 条** |
| 源码 `add()` 注册处 | **30 处**（含 4 处分支重复） |
| **实跑输出** | **26 PASS + 1 SKIP = 27** |

**意义**：这不是"文档笔误"级别的细节。它证明**研讨与扫描全程在引用二手数字、却没有任何一步在核对数字本身**——而"以错数为基数的估算"（如"25 条网 1:1 平移成 unittest）会**带着偏差进入开发文档**。`[S4]` 甚至**只纠正到 25（也是错的）**。这正是我 A1「检查器不可信」的元层版本：**连检查器的元数据（用例数）都不可信**。

**② 第二层：本机的 SKIP 是"永久态"，不是"临时态"。**
同一实跑里，`.sh` 的 bash 检查 SKIP 原因写死为"bash 不可用（WSL 无发行版 / 无 Git Bash）→ 记未验证"，且我实测触发了沙箱拦截：`PROGRAM BLOCKED… wsl.exe … Program Blacklist`。而 `[HT2]` 附录 B 证明：**交互 Git Bash 可用，但 python 子进程 spawn bash 被沙箱拉黑**。
→ **在这台机器上，`.sh` 的那一道 Gate 永远走 SKIP**。这直接影响 D-09 与我 R1 提的"连续 N 次跳过 → 升 FAIL"：**那是错的，会立即误伤**（把"环境能力缺失"误判成"逃逸"）。修正见 §C。

**③ 第三条：`/models` 现在富到可以当"能力协商表"用，这改变 D-13/D-12③ 的形态。**
`[S1]` F8 实测字段含 `context_window / max_output_tokens / effort.supported_levels / effort.default_level`。→ 分母**不必硬编码**（`[S1]` 结论），且 **effort 也能做双向核对**（见 §D-F4 的可探测判据）。

## §B 交叉互审质疑（K3 六要素）

### B-1｜对 HT1-设计者 · 把"需网才能验"的环焊进"可离线验"的链，是新的风险传染

- **问题**：HT1 主张 P2 为"**一条有向依赖链一次做完**"：`token_ledger（新建）→ D-11 → D-12③/D-13/compress`。方向对，但这条链**横跨"可离线验证"与"只能靠网络验证"两界**：`token_ledger` 的写入接口、`D-14` 函数可离线；`D-11 真调用`、`D-12③ 档位`、`D-13 enforcement`、`compress-LC3` **全部必须真联网才能验**。
- **影响**：捆绑交付时，**一半是可判定的、一半是不可判定的**，验收时只要有一环没网就整链"未验证"；更糟的是为让链"跑通"，会有人给联网环**造 mock**——`[S1]` F9/F11/F19 三个方言坑（`[DONE]` 哨兵 / usage 附在最后内容块 / `: keep-alive` 注释行）**在 mock 里全都不会出现**，于是自测全绿、真调用照样挂。
- **等级**：**P1**（重演"引擎化=假绿"）
- **证据**：`[S1]` F9/F11/F19；`[HT2]` 质疑 1（真熔断三前提"一条都不成立"）；`[S4]` R5（现有网里已有"形式通过"的先例：用例 7 只跑 `bash -n`）。
- **建议**：**链保留，但切成"离线半链 + 联网半链"**：P2 只交**离线半链**（`token_ledger` 写入接口 + `route_error` + 自测网 + cli 转发）；**联网半链**（真调用 / 档位 / enforcement / LC3）挂"探针 via"后置（见 §D-F1）。**链的依赖关系写进文档，但交付边界按"能否离线验证"切**。
- **证据增益**：避免"为让链跑通而造 mock"——这是本框架最贵的失败模式（自测绿、真调用挂）。

### B-2｜对 HT1-设计者 · 参数单点定义了，但**没人校验参数没被改坏**

- **问题**：HT1 的 D-18 改法很好（"阈值/参数单点定义，代码只引用不复制"），但**缺一环**：`engine_config`（无论放 `SKILL.md` 参数块还是 `references/engine_config.md`）是**人可编辑的**。若有人（或 AI）把 `reasoning_effort` 写成 `minimal`、把预算上限写成 `0`、把温度写成 `5.0`——**代码读进去照样执行，没有一层校验**。
- **影响**：这与 rule 18「过度服从/合约矛盾也照做」同族：**参数是真相源，但真相源无 schema**。而且它**比代码 bug 更隐蔽**——配置漂移不出 Traceback。
- **等级**：**P1**
- **证据**：`[S1]` F15（`minimal→low`、`medium/xhigh→high` 是**兼容映射**，不是错误——意味着"写了 minimal 你以为更省，其实被映射成 low"，**静默语义变更**）；`[S4]`（`fastjsonschema` 1 包 26.8 KB 是唯一保住纯 Python 的 schema 方案）。
- **建议**：`engine_config` 每个键必须有 **schema + 合法域**（手写校验或 vendored `fastjsonschema`）；引擎启动**校验并在非法时 FAIL**（不许静默取默认）；`[S1]` 的兼容映射（`minimal→low`）必须在配置里**显式登记为"已知等价类"**，否则它就是一条静默假绿。
- **证据增益**：把"参数单一来源"从**承诺**变成**可 grep 校验的约束**。

### B-3｜对 HT3-用户 · 你的前置问题问错了对象，结论会砍少（或砍错）

- **问题**：HT3 的核心前置是"**现在到底有没有任何脚本需要自己调 LLM？**"答否 → 不做 D-11。**结论方向我同意**，但问法漏了：**引擎自身就要调 LLM**——rule 83 的 **LC3 结构化摘要是唯一花 LLM 的一层**（`context_compression.md:38`）；D-14 的"无法判断→human"兜底也可能要 LLM。
- **影响**：按 HT3 的问法，只要"业务脚本不调 LLM"就能砍 D-11；但**引擎自用的 LC3 摘要需求是独立存在的**。若照 HT3 砍干净，则 `compress` 只能做 LC1/LC2（不花 LLM 的两层），LC3 永远缺位——**看似省了，实则留一个"半截功能"**。
- **等级**：**P1**（会砍少一半，或砍错范围）
- **证据**：`references/context_compression.md:35`「LC3 结构化摘要…**（唯一花 LLM 的一层）**」；讨论文档 D-15 把 `compress`（rule 83 三级级联）列进命令面。
- **建议**：把前置问题**升级**为："**引擎自身（非业务脚本）要不要调 LLM？**"——若答否，则 `D-11 / D-13 / compress-LC3` **一起砍**，`compress` 只留 LC1/LC2；若答是，则 D-11 是**引擎自用**的基础设施（不是给"将来迁移"预造的空壳）。**这其实强化了你的结论（可砍更多），但把范围划准。**
- **证据增益**：砍的时候一次砍干净，不留半截功能——"半截功能"正是最容易被误报为"已完成"的东西。

### B-4｜对 HT2-实现者 · "引擎输出物无凭据"漏了仓库面与分发面

- **问题**：HT2 把 D-20 改写成「**引擎输出物无凭据**」（cost_log/日志/progress 不写 key + 日志脱敏）。这个重定义我同意，但它**只覆盖了"引擎跑的产物"**，没覆盖两条更危险的路径：① **仓库本身**（若 `models.json` 的路径/内容被写进 `references/` 或 `knowledge/`，`push_to_remote.sh` 一跑就带 key 上远端）；② **三平台分发副本**（`[S3]` 证明三平台各有一份代码；若其中一份的配置含 key，分发=泄露）。
- **影响**：HT2 实测**已确认** `~/.workbuddy/models.json` 明文存 apiKey（本机事实）。**风险不在"引擎会不会写"，在"仓库会不会带"。**
- **等级**：**P1**（合规 / 一次性不可逆）
- **证据**：`[HT2]` 附录 D「apiKey 明文落盘」；仓库根实测存在 `push_to_remote.sh`（会推到远端）与 `sync_to_platforms.sh/.ps1`（会复制三份）；`[S4]` 的 `-O` 提醒"别人用 `-O` 跑你的脚本"= **正是 D-20 的"给他人用"场景**。
- **建议**：把防线从"输出物"扩到**三条硬 Gate**：① 交付/推送前 `grep -riE 'sk-[a-z0-9]{16,}'` 扫**全仓**（含 `references/`、`knowledge/`、三平台目录），命中即 FAIL；② 核对 `.gitignore` 是否覆盖本机配置；③ 引擎加载配置后**立刻遮蔽**（内存外不出现明文），错误信息里 key 前缀打码。
- **证据增益**：把"合规"从**运行时纪律**变成**提交时 Gate**——纪律靠人记，Gate 不靠。

## §D 修订后的五个焦点结论

### F1 · P2 的范围与形态 —— **按"能否离线验证"切成 L0/L1/L2/L3 四层**

**主张（可执行分层）**：

| 层 | 内容 | 门槛 | 交付归属 |
|---|---|---|---|
| **L0 探针层**（需网**一次**，不属引擎） | ① `/models` **双向核对**（请求 id ∈ 白名单 **且** 响应 model == 请求 id）；② 一次非流式 + 一次流式，**存真实响应为 fixture**；③ `thinking.type` / `reasoning_effort` 行为；④ `temperature` 生效性 | **无 fixture → 不许动 L2** | 一次性脚本，**不进 cli 命令面** |
| **L1 离线可验**（可先做、可自测、可回滚） | `cli.py` **subprocess 转发**（+`encoding="utf-8"` + **退出码透传断言**）｜`design` Gate（**先定 schema**）｜`route_error` 纯规则函数（+合成样本单测）｜`compress` **LC1/LC2**（不花 LLM）｜自测网（`unittest`+`subTest` + **反向 fixture** + **故意扰动元用例**）｜`product-assert` 0 字节 SKIP/FAIL 区分｜状态板 **append-only（单调不减）校验**｜**`os.replace()` 原子写**｜`runtime_probe` **加 bash 能力探针** | 每条**新检查项须过"已知坏样本回灌"**：故意扰动 → 断言有 fixture 变红；**仍全绿 = 未完成** | **P2 主体，与网络无关，可停可回滚** |
| **L2 联网·只能 fixture 回归**（探针通过 + B1 试运行） | LLM 调用层（**连接层自建** + 解析内核可 vendor）｜分阶段档位（`reasoning_effort`）｜enforcement（**engine-internal only**）｜`compress` **LC3** | 必须先有 L0 fixture；自测**禁止打真网络**（`[HT2]` D-16 纪律，我同意） | **P2.5 / P3，不许与 L1 同批交付** |
| **L3 推后 / 砍** | 真熔断｜跨项目母板｜UI / 服务端｜用户极简入口页 | 出现真实需求再开 | — |

**"已知坏样本回灌"最小执行方案（L1 门槛，按性价比排序）**：

| 优先 | 回灌项 | 成本 | 做法 |
|---|---|---|---|
| **1** | `render-silent-fail` 的**注释剥离** | 极低 | `[S4]` B4 已给：把注释剥离正则改回 `re.S`，重跑网 → **必须有用例变红**；仍全绿 = 该能力没被网住（v3.19.0 的真 bug 就是它） |
| **2** | `product-assert` **归档时序** | 极低 | 把 `zip > asar` 比较反向 → 现有用例 11 已含反向，**验证它真的会红**（不是走形式） |
| **3** | `active-tree` **四证据** | 低 | 删掉一个证据（如运行时痕迹）→ 断言 4/5 条变红 |
| **4** | `dispatch-check` / `write-conflict` | 中 | 造一个"两模块写同一文件"的任务卡 → 断言 `write-conflict` FAIL |
| **5** | `cost_log` 定长行 | 中 | 写一条缺第 6 列的行 → `summary` 必须报不合规（现有用例 23 已部分覆盖，需确认它**断言的是"报错"而非"跑完"**） |
| **6** | 用例 7（`bash -n`） | 低但结论已知 | 直接**判定为"形式通过"**，升级为 ShellCheck 或**显式标 SKIP + 未验证**（`[S4]` R5） |

**一句话**：**P2 = L1 全做 + L0 探针一次；L2 一律"探针 via + B1"，不许与 L1 同批。** 这与 HT1 的"一次做完一条链"**不同**，也不是 HT2 的纯拆分——**分歧点：链条照留，但交付边界按"能否离线验证"切**。

**置信度：高**（有 `[S1]`-`[S4]` + HT2 实测 + 我自产实跑支撑）

### F2 · D-11 LLM 调用层形态 —— **先探针；探针后才谈形态；解析内核可 vendor，连接层必须自建**

- **结论**：`sseclient-py` 把风险**部分**转移（解析内核 → vendored 审计），但**消解不了 `[DONE]` 哨兵 / usage 落点 / 代理证书超时 / 无 tokenizer**（`[S2]` R3 自陈 + `[S1]` F11/F19 + `[HT2]` 附录 F）。因为我 R1 主张的**探针前置**（A3 双向核对）现在是**已证实的必要性**（200 假绿活体），我的立场**不变**。
- **200 假绿的通用防线**（用户点名要的"不只模型 id"）——**四步，任何 API 都适用**：
  1. **响应回显核对**：响应里的"身份字段"（`model` / `id` / `version`）**必须等于**请求的身份字段；**不等即 FAIL**（不是 warn）。这是抓住 `deepseek-v4-flash → deepseek-flash` 的那一招。
  2. **能力协商核对**：凡有"能力清单"端点（如 `/models` 的 `effort.supported_levels` / `context_window`），**请求参数必须 ∈ 清单**；越界即 FAIL（防静默回落）。
  3. **语义指纹**（抓"200 但语义被改"）：同一请求**两端参数**（如 `reasoning_effort=none` vs `max`）跑 N≥2 次，比对**机器可读的差异指标**（`usage.*_tokens`、`finish_reason`、`model`）；**两端无差异 = 参数未生效 = FAIL**。
  4. **禁用"透明修复"类组件**：`[S4]` 实测 `json-repair` **默认流程就是"先 `loads`，失败则回退修复且回退透明、无 API 告知修过没有"** —— 这**恰好制造 D-12① 要防的静默回退**。→ **禁止在解析链里引入任何"透明修复"**。
- **置信度：高**

### F3 · D-13 enforcement —— **数据源改 provider usage（不变）+ 分母读 `/models`（新增）+ 范围收窄为 engine-internal only + fail-closed（不变）**

- **结论**：`[S1]` 只解决**分母**（可从 `/models` 读 `max_output_tokens`，替代硬编码初值）。**分子与覆盖率问题未解**，且 `[HT2]` 反向证实"子 Agent 走原生 Agent 工具直调，不经过 cli.py" → 引擎**拦不住**绝大多数调用。
- **增量（我的新判定）**：把 D-13 的适用域**显式写成"仅覆盖引擎自己发起的调用"**；对"引擎外调用"只做**事后对账**（provider `usage` 之和 vs `cost_log` 汇总，差值 > X% 告警）。**若 L2 全砍（HT3 的前置答"否"），则 D-13 的覆盖率 = 0 × 0 = 空转** → 这条**必须挂 F-准入问题**，不许先建。
- **置信度：高**（覆盖率结论）；**中**（"事后对账"阈值 X 需实测标定）

### F4 · D-12③ 分阶段档位 —— **驳回 temperature，改用 `reasoning_effort`；给三条可探测判据**

- **结论**：`temperature` 在 thinking mode 下**无效**（`[S1]` F13，且 `thinking` **默认 enabled**）→ **驳回原形**。
- **真的生效 + 可探测的实现（用户点名要的）**：
  1. **参数替换**：档位用 `reasoning_effort`（`[S1]` F15：`none|low|high|max`，默认 `high`）；`temperature` 从调用契约中**移除**，或仅在显式 `thinking:{type:"disabled"}` 时保留（**二选一，不许两存**）。
  2. **判据① 能力协商（启动时，硬 Gate）**：`GET /models` → 读 `effort.supported_levels`；请求的 effort **必须 ∈ supported_levels**，否则 FAIL（**不静默回落**）。与"模型 id 双向核对"同构，**把 effort 也纳入双向核对**。
  3. **判据② 机器可读的生效证据（一次性 + 定期）**：同 prompt、`reasoning_effort` 取两端（`none` vs `max`），各跑 N≥3–5 次，比对 **`usage.completion_tokens_details.reasoning_tokens`**（`[S1]` F12 该字段存在）——`none` 应≈0、`max` 应显著 >0。**若两端无显著差 → effort 未生效 → FAIL**。（这是**不依赖主观判断**的判据，优于 HT1/HT2 的"跑一遍看看"。）
  4. **判据③ 兼容映射显式登记**：`[S1]` F15 的 `minimal→low`、`medium/xhigh→high` 是**静默语义变更** → 必须在 `engine_config` 里登记为"已知等价类"，否则"写了 minimal 以为更省"就是静默假绿。
  5. **档位→effort 单点映射**：`lite→none|low` / `default→high` / `reasoning→max`，写进 `engine_config`（受 §B-2 的 schema 校验）。
- **置信度：高**（驳回）；**中**（判据②的"显著差"阈值需实测标定）

### F5 · D-02 / D-03 是否升"框架级标配" —— **降级 B1（不变）**

- **结论不变**：无第二项目复现证据；`[S4]` 的"数字四口径"是旁证。**升"标配"= 用一个未被证实的机制，去换所有项目的常态负担**（HT3 的"确认疲劳"与我同向）。
- **D-02 校验器（c）的额外红线**：`[HT2]` 说得很对——**脚本无法知道"用户做没做某动作"，只能判断"文件改没改"**。所以 (c) 只能做 **append-only（单调不减）结构校验**，**"自动生成事件流"必须删**（否则就是伪造证据）。
- **置信度：高**

## §E 红队视角 · 3 条新角度（含元层）

### E-1｜元层：**研讨流程本身从未核对过它引用的数字**（本件自产证据）

- **角度**：A1「检查器说不可信」之上还有一层——**研讨流程的输入是二手、未核对的**。同一件事（自测用例数）出现 **24 / 25 / 30 / 27** 四个数字，其中**讨论文档错、扫描（`[S4]`）的"纠正值"也错**。
- **若不成立**：若这个数字进了开发文档的"P2 验收口"（如"25 条 fixture 1:1 平移"），验收就会拿一个**错的基数**去核对，**永远对不上或永远"通过"**。
- **最小防线**：开发文档里**一切"现状数字"必须由脚本自报**（跑一次贴输出），**禁止人手抄**。本件已示范（`总计：26 PASS / 0 FAIL / 1 SKIP`）。

### E-2｜失败路径：**本机的 SKIP 是"永久态"，任何"降级留痕"若不先探能力，就是永久逃逸**

- **角度**：我在 §C-3 自我修正的延伸。D-09 的"脚本不可用→降级留痕"在本机**不是偶发分支，是常态路径**（`.sh` Gate 因 `wsl.exe` 沙箱黑名单**永远 SKIP**）。若"降级留痕"只写文件不升级，则**三平台一致性里最有价值的 `.sh` 侧检查，长期为"未验证"**。
- **若不成立**：所有 `.sh` 相关规则**事实上未被执行**，但报告显示"已降级留痕"（= 体面的未验证）。
- **最小防线**：**能力探针优先于降级**——先跑 `runtime_probe`（需加 bash 探针，`[HT2]` D-09 建议，我同意）判定"该能力在本机是否存在"；**存在却跳过 → 计数升 FAIL；不存在 → 显式标 `[不可测·环境缺失]`**（`[S4]`/R-008 已有此口径）。

### E-3｜依赖变化：**vendor 的 `sseclient-py` 会被"只增不删 + 三平台分发"冻结成三份无人升级的代码**

- **角度**：`[S2]` 提了 vendor 是第四条路，但**没人算它的生命周期**。本框架有两条既有纪律叠加：**只增不删**（§七.5）+ **三平台只读副本**（D-09）→ 一旦 vendor，这份代码进入 **3 个副本 × 只增不删** 的容器。
- **若不成立**：provider 改流式方言（`[S1]` 已证 DeepSeek 与 OpenAI **不同**：usage 无独立块）→ 三个副本**各自静默失效**，且因为"只增不删"，**没人敢删旧的**。
- **最小防线**：vendor 目录建 `VENDORED.md`（版本 + 来源 URL + 引入日期 + **升级触发条件**），并把它列入"provider 方言变化时必查清单"；**三平台同步时对 vendor 文件做 MD5 一致性校验**（`sync_to_platforms` 已有 MD5 机制，复用即可）。

## §G 一句话总结

**我对 F1 的最终主张**：**P2 = L1（离线可验全做：cli 转发 + design/route_error/compress-LC1-LC2 + 自测网 + 原子写 + 能力探针）+ L0（一次性探针，产出 fixture）；L2（真 LLM 层 / 档位 / enforcement / LC3）一律"探针 via + B1 试运行"，绝不与 L1 同批交付**——链照留，但**交付边界按"能否离线验证"切**。

**"最可能让整个引擎化翻车的那一条"——变了，变得更靠外一层，且更硬**：R1 我说是「引擎（检查器）说真话」；**v2 我升级为「检查器的元数据也不可信 —— 即在'它有没有在跑'这件事上，我们连数字都是错的」**。理由：v3.19.0 证明检查器会**说谎**（假红+假阴）；`[S4]` 证明网里已有**形式通过**项（用例 7 只跑 `bash -n`）、且 `assert` 可被 `-O` 静默关掉；**我实跑又证明连"几条用例"都有四个互相矛盾的数字（24/25/30/27）**。当"某能力有没有被网住"这个**最基本的问题**都无法从现有文档回答时，任何"引擎化 = 更可靠"的推论都悬空。**所以我要求 L1 的准入门槛不是"写了自测"，而是"每条检查项都被一条已知坏样本证明过它真的会红"。**
