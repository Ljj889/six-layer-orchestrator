## §1 A3-1 cli 形态：**in-process**（带一个强制前提）｜置信度 **中**

- **一句话理由**：从家俊角度，判据不是"快 13×"，而是"**哪个更不容易悄悄地坏掉**"。两者都能防"吞退出码"，但**我们的解药已经冻结在 D-16 里**（反向 fixture 强制）——in-process 的唯一风险（`SystemExit` 被捕获后 `return 0`）**恰好被那条冻结的机制正面覆盖**；而 subprocess 反而自带一类 **Windows 中文乱码**风险（HT2 补充2），且本机是**单人自用、7 脚本同源仓库同 Python**，subprocess 的"隔离"收益基本是理论值（纯 stdlib 脚本不会崩解释器）。
- **边界**：**in-process 若不带下面第 1 条反向 fixture，我立刻改投 subprocess。** 这不是技术偏好，是"家俊没人替他复核，只能靠机制兜底"。
- **最小实现要点（≤5）**：
  1. `sys.argv = ["<脚本名>"] + argv` 后调 `module.main()`，捕 `SystemExit` → 取 `e.code`（`None` 记 0）。
  2. **严禁**捕获后 `return 0`：所有异常出口统一走"非零退出"，防堆栈被吞。
  3. 每模块 import 一次、按需调用（[复测1] 已验证 7/7 有 `__main__` 守卫、顶层零副作用）。
  4. 统一 `--project` → 翻译成三种调用约定（verb-first / dir-first / argparse，HT2 实测附录 C）。
  5. `six_layer_check` 内部自 spawn subprocess 属正常（HT2 §A-②），不在拦截范围。
- **必测断言（=3）**：
  1. **反向 fixture（强制）**：喂一个**已知 FAIL** 的子命令 → `cli` 必须 `exit ≠ 0`。这条不通过，A3-1 结论作废。
  2. 成功子命令 → `exit == 0` 且 stdout 含关键行（防"静默空跑"）。
  3. 三种约定各跑一次，argv 翻译正确（防 dir-first 被当成 verb-first）。
- **不同意谁**：**不反对 HT4 的 subprocess**（它的隔离收益真实但本机≈0）；**附议 HT2 的 in-process 翻转**，但把"6/6 保退出码"从**原型事实**升为**长期约束**（它必须在自测网里常驻，而不是一次性原型跑通就算数）。

## §2 A3-2 D-02/03 最小形态：**(iii) 弱校验 + 写明边界 + 完整性靠"AI 主动问"（非脚本）**｜置信度 **中**

- **一句话理由**：我不坚持 (i) 了——(iii) 成本≈0，且它**能抓到一类真实故障**：多脚本并发写 / 覆盖导致的**事件流被截断或行数变少**（[HT2 补充1] 的 `load→改→全量覆盖` 已知会丢更新）。**别为了砍而砍，(iii) 这条我接受**；但绝不能让它冒充"完整性校验"。
- **改判说明（有依据，非无证据翻转）**：R2 我选 (i)，理由是"脚本判不了用户动作"——这仍然成立，**但 (iii) 要防的不是"漏记"，是"截断"**，是两回事。我把 (i)→(iii) 的触发证据写清：**HT2 补充1（并发写丢更新）证明"行数变少"是真实故障**，而 (i) 对它零防御。
- **硬要求（防它自己变新假绿源）**：
  1. **必须删"自动生成事件流"**（[HT4 R2] 已承认；[HT2] 已确认脚本判不了用户动作）——我附议，写进开发文档。
  2. 报告输出必须显式打印一行 **`[WEAK-CHECK] 只判结构合法 + 行数单调不减`**。
  3. **完整性（"AI 忘了写"）不由脚本承担** → 由 **AI 在每个 Gate/换窗处主动问"本周期你做了什么跨窗动作"**（承接 R2 已收敛的 D-22"AI 主动问"）。这是流程，不是脚本。
- **「它不保证什么」（必填）**：**它不保证事件流完整——"AI 漏写了一行"这类缺行它一定漏报；它只保证"没有被截断/被重写变少 + 结构没坏"。**

## §3 A3-3 P2 默认范围：**默认 = L1 中"不预设需求假设"的 6 件；design / route_error / compress 三件挂 pending**｜置信度 **中**

- **一句话理由**：我把判据**逐件**过一遍，结论不是"只 cli+自测网"（我 R2 的说法），而是"**边界 = 不预设需求假设**"。L1 里有 6 件过、3 件不过。这是**边界细化（有依据）**，不是翻转——我当时给的"只 cli+自测网"是举两个例子，判据一直是同一条。
- **默认做（6 件，均"即使低频也正向"）**：`cli.py` 串联 ｜ 自测网 ｜ `os.replace` 原子写 ｜ `runtime_probe` bash 探针 ｜ 状态板弱校验(A3-2 iii) ｜ product-assert 时序。
- **挂 pending（3 件，各自需要一个还不存在的对象）**：
  - **`route_error`** → 需要**真实 FAIL 语料**才验得准（HT2："回归集是人工标注脏活，样本可能很少"；样本=1）→ **预设了"家俊会持续产出足量 FAIL"**。
  - **`compress`(LC1/LC2)** → 需要**真实长会话**才触发（rule 83 已有"分母错→永不触发"先例）→ **预设了"会话会长到需要压缩"**。
  - **`design`(schema)** → 需要**设计锁定产物**才有对象（HT2 实测"现有 7 脚本无任何设计产物 schema"）→ **预设了"家俊会走设计锁定"**。
- **一行回退**：**若家俊答"频率很低 / 主战场（家具店运营）不走框架" → 回退为 `cli 串联 + 自测网 + os.replace` 三件纯基础设施**，其余（含 pending 三件）一律不解挂。
- **对 HT3 判据的正面回答（逐件一句）**：
  - `cli.py` 串联：**不预设**——只降 AI 摩擦，与频率无关。
  - 自测网：**不预设**——是资产，任何频率正向。
  - `os.replace` 原子写：**不预设**——纯正确性修复，防丢更新。
  - `runtime_probe` bash 探针：**不预设**——记录环境事实，[HT2 实测] 证明降级口正在被使用。
  - 状态板弱校验(iii)：**不预设**——只防截断，成本≈0。
  - product-assert 时序：**不预设**——扩已有 rule 79 底座，无新对象依赖。
  - `route_error`：**预设**（真实 FAIL 语料）→ pending。
  - `compress`：**预设**（真实长会话）→ pending。
  - `design`：**预设**（设计锁定产物）→ pending。
- **给 L1 派的正面答复**：你们 9 件里有 6 件我接受（**没为了砍而砍**）；分歧只剩 3 件，且这 3 件不是"不能做"，是"**要在真实对象出现后做**"——**这是范围边界之争，不是方向对立，本轮可收敛。**

## 最终主张 · 收敛判定 · 决策点

**三个焦点最终主张**：
- **A3-1**：**in-process**，但**强制**"已知 FAIL → 非零退出"反向 fixture 常驻自测网；无此前提则改 subprocess。
- **A3-2**：**(iii) 弱校验 + 明文边界 + 删自动生成 + 完整性靠 AI 主动问**；接受 (iii) 是因为它防"截断"，不是防"漏记"。
- **A3-3**：**默认 = 6 件不预设需求假设的基础设施**；`design`/`route_error`/`compress` **挂 pending**；回退 = `cli + 自测网 + os.replace`。

**本轮是否可收敛**：**可收敛**。三个焦点我都有明确主张；A3-3 与 L1 派的差异已由"逐件判据"化解（6 接受 / 3 挂起），属边界宽度而非方向对立；A3-1 与 HT2 同向、与 HT4 的 subprocess 差异有明确的技术解释且非原则冲突。
