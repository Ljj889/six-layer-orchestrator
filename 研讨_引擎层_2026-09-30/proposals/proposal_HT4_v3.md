## §1 A3-1 cli 形态：**in-process 包裹为默认 + `--isolate` 逃生口** ｜置信度 **高**

- **一句话理由**：证据迫使我改。`[复测1]`（7 模块 import OK/0.031s、**7/7 有 `__main__` 守卫**、顶层零副作用）+ `[复测4]`（main 契约已定位：成功 `None`／失败 `SystemExit(1)`／`six_layer_check` 成功 `SystemExit(0)`）+ `[复测9]`（**6/6 保住 Gate 退出码**）+ `[复测5]`（subprocess 416ms vs in-process 31ms，13×）。**我 R2 的"subprocess 转发"是未回应 `[复测9]` 的默认立场 → 撤回**。
- **本机"隔离"顾虑是否真实存在？——存在，但只剩 3 个可指名的向量，且都不是"必须起进程"的理由**：
  1. `sys.stdout.reconfigure(encoding="utf-8")` **全局生效**（`cost_log.py:161` / `runtime_probe.py:136` / `six_layer_check` 都做）——in-process 下会泄漏给后续命令；**但无害**（三者都是转到 utf-8）。
  2. `sys.argv` 被改写 → **是包装层责任**，必须快照/还原。
  3. 未来若有脚本 `os.chdir` 或配 root logger → 会泄漏（**当前 7 脚本无此行为**）。
  → **真正要防的是"Gate 退出码被吞"（`[S3]` 警告），而这恰恰是 in-process 归一化能解决的（已 6/6 实测）**；不是"进程污染"。
- **最小实现要点（≤5）**：
  1. 懒加载 `importlib.import_module(脚本名)`（避免启动即全量 import）。
  2. 每次调用：`old = sys.argv[:]` → `sys.argv=[名]+翻译后 argv` → `rc = mod.main()` → `except SystemExit as e:` `rc = e.code if isinstance(e.code,int) else (0 if e.code is None else 1)` → `finally: sys.argv = old`。
  3. `except Exception`（非 SystemExit）→ **打印 traceback + rc=1**（不静默吞、不静默成功）。
  4. **stdout 归属**：调用前后各打 `[cli] >>> <cmd>` / `[cli] <<< <cmd> rc=<n>`（in-process 共享 stdout，必须能定位输出属于哪条命令）。
  5. `--isolate` 逃生口走 subprocess（`encoding="utf-8"` + 显式超时），用于排错/怀疑污染时；保留 `--project` 显式传参。
- **必测断言（3）**：
  - **A（失败透传）**：`checkpoint <dir> status`（非法状态）/ `cost_log <dir> add … 非法档位` / `lifecycle <dir> transit`（非法转移）→ cli 退出码 **必须 == 1**。
  - **B（成功透传）**：合法命令 + `six_layer_check self-test` → cli 退出码 **== 0**。
  - **C（无污染）**：同进程连跑「失败命令 → 成功命令」→ 后者 rc==0，且断言 `sys.argv[0]` 未漂移。
- **诚实保留的代价（不推翻结论）**：in-process **失去 per-command 超时边界**（一条命令挂住会卡整个 cli）。L1 命令都是本地短任务，**本轮可接受**；这条正是 `--isolate` 存在的理由。

## §2 A3-2 D-02/03 最小形态：**选 (iii) 模板 + 规则 + append-only 弱校验** ｜置信度 **高**

- **一句话理由**：**HT1 质疑 3 成立**——弱校验（结构合法 + 行数单调不减）**不需要"该有几行"的基线**，我 R1 用"并发基线未解"把 (c) **整体否掉**属**过度**；且我 R1 §6 自己写的"校验事件流行数而非文件存在"**就是 (iii) 本身**，两处自相矛盾 → **翻转到 (iii)**。
- **它保证什么（可直接写进开发文档）**：
  > `status check` 保证：状态板文件存在、三分区结构合法（三区标题齐全、事件流区在文末且只追加）、且**事件流区行数相对上一次校验记录单调不减**（append-only 未被破坏）；任一不成立即 FAIL。
- **它不保证什么（必填）**：
  > `status check` **不保证"用户动作都被记入"**（漏记、忘记一律不报），不校验内容真伪，也不判定"该有几行"——**弱校验通过 ≠ 事件流完整**，不得据此声称"跨窗口信息已无遗漏"。
- **残留要求（我 A11 的合理内核，降为一条实现约束）**：单调性的**基线不得**来自"会被并发读改写（read-modify-write）的文件"——用 `git diff --numstat`（只读）或独立 append-only 的 `status_check.log`（自身也 append）。**禁止**把基线写回 `progress.json` 的读-改-写（那正是丢更新点）。
- **生成器**：不做（脚本无法知道用户做没做动作，HT2 论据成立）。(iv) 的 pending 部分与 F5 的 B1 试运行合并，不另立。

## §3 A3-3 P2 默认范围：**默认 = L1 全做，但内部拆 L1a / L1b** ｜置信度 **中高**

- **一句话理由**：默认不取 HT3 的"只 cli+自测网"（L1b 成本低且不阻塞），但也**不能照单全收"L1 全部不预设需求"**——那只有 4/9 件真成立（下表）。
  - **L1a（不预设需求，无条件做）**：`cli.py` 串联｜自测网｜`os.replace()` 原子写｜`runtime_probe` 加固。
  - **L1b（预设"对应流程会跑"，挂频率轻门，排期在 L1a 之后）**：`route_error`｜`compress` LC1/LC2｜`design`(schema)｜`product-assert` 时序｜状态板弱校验。
- **一行回退（D-21 约定）**：
  > 若家俊答"过去 30 天框架使用 ≤2 次 / 主战场（家具店）不走框架" → **回退为只做 L1a**，L1b 与 L2 一并挂起（出现真实调用点再开）；**不删任何冻结条目**（D-01…D-22 规则层照进 P1）。
- **对 HT3 判据的正面回答（逐件）**：
  | 件 | 不预设需求？ | 理由 |
  |---|---|---|
  | cli 串联 | ✅ 是 | 减"记不住 7 个脚本路径"的摩擦，与频率无关 |
  | 自测网 | ✅ 是 | 提升**既有 Gate 的质量**，不依赖谁用什么功能 |
  | `os.replace` 原子写 | ✅ 是 | 修**存量脚本**丢更新 bug（checkpoint/lifecycle），无条件正向 |
  | `runtime_probe` 加固 | ✅ 是 | 修**存量探针**，与使用频率无关 |
  | `route_error` | ⚠️ 否 | 只在"有审查 FAIL 需路由"时生效，低频=永不触发 |
  | `compress` LC1/LC2 | ⚠️ 否 | 只在"上下文长到需压"时生效 |
  | `design`(schema) | ⚠️ 否 | 只在"走设计锁定流程"时生效 |
  | `product-assert` 时序 | ⚠️ 否 | 只在"有打包产物"的项目生效 |
  | 状态板弱校验 | ⚠️ 否 | 只在"建了状态板"时生效（板本身已降为可选） |
- **点名 HT1 α 的两处混入（不是"需网"，是"需能力/需流程"）**：
  1. **`design` 命令**：**校验器**离线可测 ✅，但它守护的 **rule 65 设计锁定流程含"边讨论边上网调研佐证"**（`SKILL.md` Phase -1.5 原文）→ **"design 命令能跑" ≠ "设计锁定完整"**（又一次假绿），开发文档必须写这句留白。
  2. **`runtime_probe` 的 bash 探针**：**不是需网，是会触发沙箱拦截**——我实测 `wsl.exe` 在 Program Blacklist，`sync_to_platforms.sh` 的 bash 检查**永远 SKIP**。探针必须建成**三态（ok / missing / blocked）**，**`blocked ≠ missing`**，否则探针自身会异常退出（或更糟：被当成 missing 而降级）。
