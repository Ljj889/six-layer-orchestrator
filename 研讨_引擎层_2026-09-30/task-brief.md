## 1. 项目背景（30 秒版）

家俊（21 岁，广州民航职院大数据 → 2027 升广东科技技术学院本科）自建了一套「多 agent 六层联合编排框架」，用于让 AI 按严谨流程（Phase -2 调研 → 规格 → 设计锁定 → 拆模块并行开发 → 独立审查 → 合并 → 经验蒸馏）开发他的真实项目（家具店线上运营、伴学 App 等）。

**现状**：框架是**提示词驱动**的（`SKILL.md` 是规则真相源，由 Agent 读提示词自觉遵守）。已有 7 个 Python 脚本做"能硬约束的那部分"（合规闸 / 断点 / 账本 / 状态机 / 探针 / 校验 / 知识读取）。

**本次要解决的问题**：把"只能靠自觉"的部分**下沉为引擎**（Python 硬代码），并同时落地一轮从「伴学 P0 实战」蒸馏出的规则。**上限：规则层 + 引擎层，不做平台化外壳/UI。**

## 2. 硬约束（所有方案必须遵守，违者 P0）

1. **零依赖优先（D-11 已建议）**：引擎要能被任意平台跑（只要有 python + stdlib）。第三方依赖越少越长寿。**"任何要装第三方依赖的决策须过尽调"是框架既有规则**。
2. **可移植 + 无凭据落盘（D-20）**：按"将来可能给他人用"的纪律写（API Key 不落盘/不硬编码，用环境变量或本机配置）。
3. **规则真相源不动摇（D-18）**：`SKILL.md` 保留为规则真相源，引擎只做"能硬约束的部分"，不把规则语义下沉进代码导致人不可读。
4. **只增不删（§七）**：现有 7 个脚本是资产，**只加不改**（除 bug）；规则编号体系改动契约不动（编号只增、删除号留空）。
5. **新命令必须带自测用例（D-16 建议）**：否则视为未完成（硬 Gate）。
6. **单人自用为主**：不预设多租户/团队权限/计费/UI。
7. **本机环境事实**：Windows + 受限 agent 环境（Bash 残废、PowerShell 5.1 四坑、沙箱删除护栏）。Python 托管版 3.14.3 / 3.13.12；Node 22.22.2。**已知坏的：`py` 启动器**。
8. **异构降级声明**：本机 `~/.workbuddy/models.json` 只注册 **1 个模型**（`deepseek-v4-flash`）→ 本次研讨**无法做真模型异构**，已在方案顶部显式标注"异构降级"，用**强差异化提示 + 推理档位差异**替代。

## 4. HT 任务与输出纪律

### 4.1 四个 HT（视角必须不重叠）

| HT | 视角 | 默认立场 | 模型/档位 |
|---|---|---|---|
| **HT-设计者** | 方案本身（目标达成 / 逻辑自洽） | 为方案辩护（收敛锚） | default |
| **HT-实现者** | 可行性（技术坑 / 依赖 / 工期 / 成本） | 专挑"做不出来 / 做歪" | default |
| **HT-用户** | 需求真伪（真实用户要吗 / 价值 / 边界） | 专挑"没人要 / 过度设计" | default |
| **HT-风险官** | 假设与边界（前提不成立 / 合规 / 回滚 / 失败模式） | 专挑"假设不成立" | **reasoning（异构降级位）** |

**每个 HT 的系统提示写死**：「你默认怀疑其他人的推理，只有当证据迫使你同意时才同意；你的职责是找出问题，不是达成和谐。」

### 4.2 Round 1 输出格式（独立盲写，互不可见）

先写 **§0 退一步**（3-5 句：这个方案真正要解决什么问题、什么情况下它会失败），然后：

**§1 逐条裁决表**（22 行，每条一行）：
```
| 编号 | 我的结论（采纳/改/驳/待定） | 一句理由 | 若"改"→改成什么 |
```
> 允许对同一条给"分阶段结论"（如 P1 采纳(a)、P2 转(c)）。
> **拿不准不许空着**，写"待定 + 我需要什么信息才能定"。

**§2 我的三条最强质疑**（对原建议中最可疑的三处，按 K3 六要素格式：问题/影响/等级/证据/建议/证据增益）。

**§3 开源复用视角**（我的角色下最该复用/最该自建的部分，2-4 条，可带具体项目名）。

**§4 我认为原文档漏掉的议题**（0-3 条，若没有写"无"——但不许为凑数硬编）。

### 4.3 三条判据（避免"感觉好看就收"，原文 §九）

1. **能不能被硬约束？** —— 只能靠自觉的规则，优先做成脚本/Gate；做不了才留提示词层。
2. **会不会增加确认疲劳？** —— 新增"必须问人"的环节要算成本；方向类必须问，执行类可异步。
3. **跨项目成立吗？** —— 只在**一个项目**验证过的东西（本轮 6 条候选）先标 `[假设]`；第二个项目复现才升 `[事实]`。

- **扫描员 A（LLM 调用层 / 错误路由 / 结构化输出）**：零依赖 HTTP+SSE 客户端参考、多 provider 统一调用、LLM 网关、重试/退避、结构化输出校验、token 计数与预算、`route_error` 类规则路由。重点回答：**D-11「零依赖」到底该自己写多少、有没有"零依赖但也成熟"的现成件**。
- **扫描员 B（CLI 框架 / 编排引擎 / 状态机）**：Python CLI 框架（argparse vs Typer vs Click）、工作流/状态机引擎（LangGraph / Prefect / Dagster / Temporal / CrewAI）、多 agent 编排框架、检查点/断点/可恢复执行、任务卡与其 lint。重点回答：**D-15 `cli.py` 该用 stdlib argparse 还是引依赖；有没有值得"整体借鉴架构"的编排引擎**。
