# Bug-Fix 轻量模式（报错修复专用）

> 版本：v1.6 | 2026-08-11 初版（家俊提出需求 + rule 46「要不要编排」出口的显式化）· 08-12 增补（番茄钟实战：协议类先找权威文档 / 协议修复必单测回归）· 08-13 增补（多宠语音实战：项目生命周期检查，rule 63；硬约束优先+纠错先检索，rule 64）· 09-12 增补（番茄宠物V2 单日实战：真实源码复现纪律 + 验收三要素，rule 41 v3.16.0 扩展）· 09-30 增补（v1.6：检索序升级为"试错前硬步骤"+ 决策卡加第 ⓿ 步，rule 64 v3.20.0 泛化）
> 用途：其他项目开发窗口遇到报错时的**标准处理流程**——强制先找根因，按根因范围选路，改完必验证。
> 定位：**轻量模式，不走完整六层**。它是 rule 55 三种运行模式之外最轻的"第 4 个参数组"——只在该走的环节走，不该走的绝不走。

---

## 何时触发

任何"改报错 / 修 bug / 排查异常"任务。触发即进入本模式，**先判断，再动手**。

## 触发前强制检查：项目生命周期状态（v1.2 · rule 63）

**先确认项目状态**（查 progress.json 的 lifecycle 字段 / 问用户）：
- **DELIVERED / REOPENED（未验收）** → **不走本模式的"路 A 直做"**——验收没过 = 项目没完成 = 六层框架模式持续生效，修改必须走分发（rule 63）：架构师改契约 / 程序员改代码 / 审查员验证。
- **ACCEPTED（已验收）或独立小 bug** → 本模式正常生效（路 A 直做可以）。
- 不确定 → 问用户"这个项目验收过了吗？没验收我按框架分发改"。

> 实战教训（多宠语音项目）：验收没过时的修改被主 Agent 当成"单文件小改动"直做，违背"调度器不写代码"铁律——因为框架没有状态机强制。rule 63 补上：**验收判定权归用户，未确认前框架不退出**。

## 第一步（强制，不可跳过）：先检索，再定位根因

**禁止凭感觉改代码，禁止直接"猜/撞"。** 动手前必须**按序检索**（v1.6 · rule 64 v3.20.0 泛化：三环是**试错前硬步骤**——三环跑完前禁止进入试错区，即任何"改一版试试 / 重跑 / 真机复现 / 重新打包"）：

0.0. **先 grep 项目内已验证的同类实现**（最廉先验，rule 64 检索序第一环 + R-011）——改任何交互/渲染/IPC/协议行为前，项目里几乎总有已经跑通的同类实现；照它做比自创稳（教训：桌宠拖拽、浮窗 setBounds 两次重造轮子，都是用户提醒后才去找已有实现）
0. **先查自己的经验库**——`read_knowledge(报错关键词/技术栈)`（rule 59）：有没有遇到过一样的问题？坑→护栏直接套用（复用不重造，别人踩过的坑别自己再撞）
0.5. **再搜网上（v1.6 强化 · 中英各搜）**——WebSearch 关键词 = **平台/库 + API/功能名 + 症状**，**中英各搜一遍**；优先官方文档 > GitHub Issues/官方论坛 > Stack Overflow/社区同解——网上有大量心得与踩坑帖，往往同一个坑别人早踩过、解法直接可搬；**结论标注来源**；绝不跳过检索直接猜
1. **看日志 / 报错输出**——完整读一遍报错栈，不只看最后一行
2. **协议/格式类问题先找权威文档（v1.1 · 番茄钟 Realtime 联调实战）**——字节布局/帧结构/鉴权头这类问题，**先查权威文档（API 文档/apifox/开源实现），不凭推断写格式**——字节布局错了最难肉眼发现，猜错一次浪费一轮（案例：decode failed → 查协议文档发现帧缺 Session ID + payload 结构错）
3. **最小复现 → 无果才试错，且试要成组（v1.6 · D48 ③）**——写最小用例复现问题（rule 41 验证归因精神：先确认"是脚本错还是代码错"）；三环检索无果、需要对比实验/改一版验证时：**一轮把候选成组比完**（多候选 + 验收断言 + 结果全部落日志），**禁止一轮押一种**
4. **找到根本原因**——能回答"为什么这里会错"，而不是"怎么让报错消失"

> 找不到根因 = 任务未完成，禁止进入第二步。根因不明就选路 B（编排调研定位），不许硬改。
> **试错前硬步骤红线（v1.6 · 家俊 2026-09-30）**：第 0.0/0/0.5 三环跑完前禁止任何试错动作——"先试一下再说" = 违规（每轮试错都烧真机往返/重跑/打包 = 最贵的资源）。子 Agent 口径：三环同样写进任务卡（task_templates 环境铁律第 4 条），回报附**检索留痕**（途径 → 来源 → 结论）——反复试错无留痕 = 按未验证处理（Red Flag「反复试错无检索留痕」）。

## 第二步：按根因范围选路

| 路 | 判定条件 | 怎么走 | 对应 rule |
|---|---|---|---|
| **路 A · 直做** | 单文件、单根因、改动小 | 单 Agent 直做（**不进入编排**）：改 → 跑验证 → cost_log 记一行理由 | rule 46 出口 |
| **路 B · 低成本编排** | 跨模块 / 根因不明 / 需调研 | 低成本模式编排：Phase -2 调研定位根因 → 架构师拆解 → 单 Agent 执行 → 审查 → 合并 | rule 55 低成本 + rule 46 |
| **路 C · 必问人** | 涉及数据迁移 / 语义变更 / 不可逆操作 | **必须升级给人**，禁止默认处理 | rule 36 |

**判定优先级**：先查路 C（数据不可逆永远问人）→ 再查路 A/B。

## 第三步（三条路都必做）：改完必验证 + 交付说明根因

1. **不跑不会发现**（rule 43）：验证两层制——dry-run 不够，关键路径至少一次真实执行
2. **边界覆盖**：测试含边界值 + 容差 + 脏数据（不是"跑通了"就完事）
3. **协议/编解码类修复必单测回归（v1.1 · 番茄钟 Realtime 联调实战）**：帧编解码是最容易错又最难肉眼发现的环节——修复后必须协议单测回归，**测试要含真实错误帧结构**（不只 happy path），如豆包 Realtime 16/16 用例含真实错误帧（400 缺头 / 401 鉴权 / decode failed）
4. **交付说明**：说"**根因是 X，改了 Y**"，不是"报错没了"——用根因证明确实修对了

## 与六层框架的关系

```
报错来了
  → 第一步：看日志/复现/找根因（强制）
  → 第二步：根因范围判断（路 A/B/C）
      ├─ 路 A → 单 Agent 直做（框架 rule 46 出口，记一行 cost_log）
      ├─ 路 B → 低成本模式编排（rule 55：1 架构师无评审、调研一层、重试 1、PASS 自动）
      └─ 路 C → 升级给人（rule 36）
  → 第三步：改完必验证（rule 43）+ 交付说明根因
```

**核心思想**：不是所有活都走六层，但**"判断该不该走六层"这个动作是强制的**。Bug-Fix 模式让"改报错"这个高频场景有标准可依——快，但不乱来。

## 长排错会话检查点（v1.4 · rule 81）

排错会话的上下文膨胀速度远超普通开发——每个"假设 → 验证 → 证伪"循环都产生大量中间输出，三轮就能击穿 rule 40 的 2,000 行目标；且上下文压缩后早期结论全部丢失（压缩即失忆）。实测教训：一次 Tailwind content 漏扫排错拖了三轮，第一轮的排除结论靠记忆兜底，险些重复排查。规则：

1. **假设证伪即落盘**：每证伪一个假设，立即在 `lessons.md`（或 scratchpad）追加一行——
   `[排错检查点] 已排除: <假设 + 证据> | 当前最大嫌疑: <X> | 下一步: <动作>`
   把"早期结论靠记忆"变成"结论固化在磁盘"，与 Pre-Compaction Flush（rule 40）同一机制。
2. **3 轮强制小结**：超过 3 个假设被证伪仍未定位根因 → 强制暂停，写一份断点小结（已排除清单 / 当前嫌疑排序 / 已试过的修复 / 下一步计划），再继续。禁止"马上就找到了"心态带病深挖（与 rule 57 重复熔断同构：排错循环也是循环，空转就停）。
3. **取证优先**：用户报现象类问题（UI 不显示/样式丢失/无响应）时，第一动作是加诊断日志 + 要标准数据 + 对照实验（rule 80），禁止未取证就改代码——标准数据集见 references/symptom_triage.md 现象排查卡。
4. **蒸馏衔接**：根因定位后，"三轮才找到的根因"是 Phase 7 蒸馏高价值候选（案例：Tailwind 漏扫 → R-008 类型门禁假绿 + rule 79 渲染端静默失效脚本化）。

## 真实源码复现（v1.5 · rule 41 v3.16.0 扩展）

"看起来一样"不等于"是同一个逻辑"——**复现与验证必须用真实源码函数 + 真实数据**：

1. **禁止逻辑复刻**：不要照抄一份"我认为它是这么写的"实现来自测——复刻通过 ≠ 原逻辑正确（复刻里已经含进了你的错误理解，等于用假设验证假设）。
2. **正确手法**：用 esbuild / tsc 转译**真实源文件片段**，提取私有函数后喂**真实数据**（真实日志里的文本、真实 DB 字段、真实报文）：
   ```js
   // 真跑，不是复刻：转译真实源码片段 → 取私有函数
   const js = require('esbuild').transformSync(src.slice(start, end), { loader: 'ts' }).code
   const mod = new Function(js + '\nreturn { mayBeOpenTagTail }')()
   ```
   完整手法（两种提取方式 + 真实数据来源清单）见 `knowledge/framework-skills/real-source-repro.md`。
3. **归因三态**：复现结论只允许三选一——`脚本错` / `代码错` / `数据不符`；未写归因就回退代码 = 违规（rule 41）。
4. **现象消失证据三要素**（与 rule 80 同口径）：**档案状态**（新档/旧档）· **代码来源**（源码/构建产物/asar）· **启动方式**（dev/packaged）——三者任一不同都不算同一验证。
5. **反证信号也要留痕**：防护生效的日志（如 `流结束丢弃未完成标签残渣`）与"现象消失"同等重要——它证明走的是防护路径，而不是碰巧没复现。

## 决策卡（可粘贴到任意开发窗口）

```
你收到一个报错/异常任务。按 Bug-Fix 轻量模式执行：
⓿ 先三环检索（试错前硬步骤——三环未跑完禁止试错，"先试一下再说"=违规）：
   ① grep 项目内已验证同类实现 ② read_knowledge 经验库
   ③ WebSearch（平台/库+API+症状，中英各搜一遍，优先官方文档/GitHub Issues，结论标来源）
① 看日志/报错输出/写最小复现，找到根本原因——找不到根因不许动手；
   三环无果才试错，且试要成组（多候选+断言+全部落日志，禁止一轮押一种）
② 判断根因范围：
   - 单文件单根因 → 直接改（不编排），改完跑验证
   - 跨模块/根因不明 → 低成本模式编排（调研定位→拆解→执行→审查）
   - 涉及数据/语义变更 → 停下问人
③ 改完必验证（不跑不会发现），交付时说明"根因是 X，改了 Y"
```
